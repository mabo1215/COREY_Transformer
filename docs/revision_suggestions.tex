\section*{AAAI 2027 Final Submission Check for COREY}

\subsection*{Overall Verdict}

The current manuscript is close to submission quality, but it should not be submitted immediately without several final corrections. The main paper appears broadly compliant with the AAAI page-limit and anonymization requirements: the technical content fits within seven pages, references occupy the final page, the manuscript is anonymized, and the PDF appears to use an acceptable submission layout. However, two issues must be fixed before submission:

\begin{enumerate}
    \item The definition of the final COREY scheduler is inconsistent across the main text, tables, and appendix.
    \item The supplementary material contains visible formatting problems that may affect reviewer confidence.
\end{enumerate}

\subsection*{Must-Fix Issue 1: Inconsistent COREY Scheduler Definition}

The largest technical risk is that the paper mixes the final calibrated scheduler with legacy scheduler results. The manuscript states that the default calibration is
\[
H_{\mathrm{ref}} = \log K,
\]
and that this calibrated rule selects the offline-oracle chunk size at the kernel level. However, several tables and paragraphs still appear to report behavior from the older legacy setting
\[
H_{\mathrm{ref}} = 8.0.
\]

This creates a serious consistency problem. In the current draft, COREY sometimes selects \texttt{chunk=512} as the default calibrated policy, while in other places it still selects \texttt{chunk=256} for similar entropy ranges. This makes it unclear which scheduler is the final submitted method.

\paragraph{Specific inconsistencies to fix.}

\begin{enumerate}
    \item Table 2 and Table 5 present COREY default with \(H_{\mathrm{ref}}=\log K\), selecting \texttt{chunk=512} and matching the Static-512 oracle.
    \item Table 3 reports Normal(0,1) with entropy around \(H=4.612\) but selects \texttt{chunk=256}. Under the stated default \(K=256\), \(\log K \approx 5.55\), so the normalized value is approximately \(0.83\), which should likely map to \texttt{chunk=512} under the paper's power-of-two rule.
    \item Table 4 still reports the H800 COREY row as \texttt{chunk=256}, while the surrounding text claims that the calibrated rule selects \texttt{chunk=512}.
    \item The prompt-level entropy distribution says all LongBench prompts map to \texttt{chunk=256}; this may be inconsistent with the final \(H_{\mathrm{ref}}=\log K\) mapping unless the row is explicitly described as legacy or runtime-hook diagnostic behavior.
    \item Several appendix sections still contain older phrasing such as ``legacy \(H_{\mathrm{ref}}=8.0\)'', ``current revision'', ``reviewer item'', and ``not yet fused-kernel evidence'', which makes the supplement read like a revision log rather than a final anonymous submission.
\end{enumerate}

\paragraph{Recommended resolution.}

Choose exactly one of the following two options.

\subparagraph{Option A: Keep \(H_{\mathrm{ref}}=\log K\) as the final default.}

If this is the final method, then all affected tables and descriptions must be synchronized. In particular, Table 3, Table 4, prompt-level chunk-bucket descriptions, cross-layer chunk-selection descriptions, and the corresponding appendix sections should be updated or relabeled so that COREY default does not alternate between \texttt{chunk=512} and \texttt{chunk=256}.

The final wording should make the following distinction explicit:

\begin{quote}
The calibrated COREY scheduler uses \(H_{\mathrm{ref}}=\log K\). Legacy results using \(H_{\mathrm{ref}}=8.0\) are reported only as sensitivity diagnostics and are not part of the final default method.
\end{quote}

\subparagraph{Option B: Do not rerun experiments.}

If the current numerical results cannot be fully updated, then the manuscript should conservatively relabel all \texttt{chunk=256} results as legacy or runtime-hook diagnostic results. In that case, the abstract and Section 5 should not claim that the data-center calibrated COREY setting matches the static oracle unless the corresponding table actually shows the calibrated setting selecting the oracle chunk.

\subsection*{Must-Fix Issue 2: Supplementary PDF Formatting Problems}

The supplementary PDF contains visible formatting problems that should be fixed before submission.

\begin{enumerate}
    \item Appendix page 3 contains severe overlap between the Table 6 caption, body text, and table content.
    \item Appendix page 18 contains a table that is too wide and is cropped beyond the page boundary.
\end{enumerate}

These problems are unlikely to cause an automatic rejection by themselves, but they reduce reviewer confidence. Since the supplementary material supports reproducibility and several key experimental claims, it should be visually clean.

\paragraph{Recommended LaTeX fixes.}

For overly wide tables, use one of the following patterns:

\begin{verbatim}
\resizebox{\linewidth}{!}{
\begin{tabular}{...}
...
\end{tabular}
}
\end{verbatim}

or

\begin{verbatim}
\begin{table*}[t]
\centering
\small
\setlength{\tabcolsep}{3pt}
\begin{tabular}{...}
...
\end{tabular}
\caption{...}
\end{table*}
\end{verbatim}

For overlapping tables, force better float placement:

\begin{verbatim}
\begin{table}[t]
\centering
...
\caption{...}
\end{table}
\end{verbatim}

If the overlap persists, move the table later in the appendix or convert it into a \texttt{table*} environment.

\subsection*{High-Priority Issue 3: Reproducibility Checklist Risk}

The reproducibility checklist currently contains several \texttt{partial} answers for source code, code appendix, hyperparameters, code release, and preprocessing. It also answers \texttt{no} for statistical significance testing.

This is risky because AAAI reviewers may treat reproducibility as part of the final evaluation. The paper should not rely only on a statement that code will be released after acceptance. It is safer to submit an anonymous supplementary code package at submission time.

\paragraph{Recommended actions.}

Submit an anonymous code and data supplement containing at least:

\begin{enumerate}
    \item scripts to reproduce Tables 2, 5, 7, 8, and 9;
    \item fixed random seeds;
    \item exact model checkpoint names;
    \item exact CUDA, PyTorch, Triton, and Python versions;
    \item prompt files or generated mixed-regime prompt lists;
    \item a README describing expected commands and expected output tables;
    \item minimal logs or CSV outputs used to generate the reported tables.
\end{enumerate}

\paragraph{Suggested checklist wording.}

For code-related checklist items, avoid overclaiming. If the code is included anonymously, use:

\begin{quote}
The anonymous supplementary package includes the benchmark harness, scheduler implementation, static chunk-sweep scripts, routed-ablation scripts, prompt lists, configuration files, and table-generation scripts needed to reproduce the main reported results.
\end{quote}

If only partial code is included, write:

\begin{quote}
The anonymous supplementary package includes the core scheduler, benchmark harnesses, and table-generation scripts. Hardware-specific patched CUDA extensions and large raw logs are summarized through exported CSV files and environment metadata.
\end{quote}

\subsection*{High-Priority Issue 4: Statistical Significance and Small Deltas}

Several reported latency differences are very small, for example \(+0.7\%\), \(+1.3\%\), and \(-0.14\%\). Without statistical tests or confidence intervals, reviewers may question whether these differences are meaningful.

\paragraph{Recommended conservative statement.}

Add the following clarification near the latency tables:

\begin{quote}
Because several measured differences are within run-to-run variation, we do not claim a statistically significant end-to-end speedup for adaptive scheduling. We report these measurements as overhead and diagnostic evidence. The main conclusion is negative: the best static chunk remains the fastest measured policy on the evaluated checkpoint workloads.
\end{quote}

\paragraph{Better option.}

Add bootstrap confidence intervals or a paired nonparametric test such as Wilcoxon signed-rank for the key latency comparisons in Table 7 and Table 8. If the differences are not significant, state that explicitly.

\subsection*{Medium-Priority Issue 5: Typographical and Notation Cleanup}

The manuscript contains several notation and wording issues that should be cleaned before submission.

\begin{enumerate}
    \item Replace all occurrences of \texttt{dinner} with \(d_{\mathrm{inner}}\) or \texttt{d\_inner}.
    \item Use one consistent notation for raw entropy and normalized entropy:
    \[
    H_b(Z) = -\sum_{k=1}^{K} p_k \log(p_k+\epsilon),
    \qquad
    \widetilde{H}(Z) = \frac{H_b(Z)}{\log K}.
    \]
    \item Avoid using \(H\), \(H_b\), and \(\widetilde{H}\) interchangeably in tables.
    \item Make clear whether each table reports raw entropy in nats or normalized entropy in \([0,1]\).
    \item Use consistent hardware names: avoid mixing ``data-center accelerator'', ``H800'', and ``server-class GPU'' unless each table explicitly defines the hardware.
\end{enumerate}

\subsection*{Medium-Priority Issue 6: Remove Revision-Process Language}

The appendix still contains wording that sounds like a response-to-review document rather than a final anonymous submission.

\paragraph{Remove or rewrite phrases such as:}

\begin{enumerate}
    \item ``R3 Minor 2'';
    \item ``Reviewer item N1'';
    \item ``current revision now adds'';
    \item ``moved from main text per reviewer request'';
    \item ``not yet fused-kernel evidence'';
    \item ``reviewers requested'';
    \item ``component status update'' where it sounds like a progress report.
\end{enumerate}

\paragraph{Suggested rewrite style.}

Instead of:

\begin{quote}
Reviewer item N1 asked whether the runtime entropy signal varies enough...
\end{quote}

write:

\begin{quote}
We further analyze whether the runtime entropy signal varies sufficiently across real prompts to justify online measurement rather than one-time static profiling.
\end{quote}

Instead of:

\begin{quote}
This table was moved from the main text per reviewer request.
\end{quote}

write:

\begin{quote}
This table provides an auxiliary diagnostic for the checkpoint-side entropy hook.
\end{quote}

\subsection*{Medium-Priority Issue 7: Theorem Numbering Consistency}

The main paper and supplementary material should use consistent theorem numbering. At present, the main text states one theorem about shared-memory depth and another about entropy majorization, while the supplement restates theorem numbers in a different order.

\paragraph{Recommended fix.}

Use globally consistent names:

\begin{enumerate}
    \item Theorem 1: Shared-memory depth bound.
    \item Theorem 2: Doubly-stochastic entropy majorization.
    \item Proposition 1 or Lemma 1: Quantization stability / \(\ell_2\)-norm preservation.
\end{enumerate}

If the Hadamard theorem is empirically falsified on real activations, keep it clearly separated from the validated COREY scheduler contribution.

\subsection*{Medium-Priority Issue 8: Clarify Hadamard Scope}

The Hadamard analysis is currently risky because the paper includes a theorem suggesting entropy growth under a sufficient condition, but then states that real Mamba activations empirically falsify the condition.

This is acceptable only if the manuscript makes the scope very clear.

\paragraph{Recommended wording.}

\begin{quote}
The Hadamard analysis is retained only as prospective low-bit theory. It is not part of the validated COREY scheduler contribution. On measured Mamba activations, the required mixing premise does not hold and the measured entropy decreases after Hadamard rotation. Therefore, no empirical claim about Hadamard-improved Mamba scheduling or quantization is made in this submission.
\end{quote}

\subsection*{Medium-Priority Issue 9: Clarify the Negative Result Framing}

The current negative-result framing is credible and should be preserved. The strongest claim is not that COREY beats static tuning, but that it closes the engineering loop and isolates why adaptive scheduling fails on the measured workload.

\paragraph{Recommended final claim.}

\begin{quote}
COREY validates entropy-guided runtime chunk scheduling as a recurrence-preserving diagnostic scaffold. However, on the evaluated Mamba-1.x checkpoint workloads, the best static chunk remains faster than all adaptive variants because the runtime decision cost exceeds the marginal benefit of online chunk selection.
\end{quote}

\paragraph{Avoid claiming:}

\begin{quote}
COREY provides a robust deployment-grade speedup over static chunk tuning.
\end{quote}

\paragraph{Acceptable claim:}

\begin{quote}
COREY demonstrates that runtime chunk routing can preserve outputs exactly, but also shows that current entropy statistics do not provide enough decision value to outperform a well-tuned static chunk on measured checkpoint workloads.
\end{quote}

\subsection*{Medium-Priority Issue 10: Improve Table Interpretation}

Some tables mix direct kernel timing, Python-dispatch harness timing, and full-checkpoint generation timing. This can confuse reviewers.

\paragraph{Recommended rule.}

Every latency table should state exactly what is measured:

\begin{enumerate}
    \item isolated Triton kernel time;
    \item Python-dispatch chunk-sweep harness time;
    \item full-checkpoint generation time;
    \item active hook overhead;
    \item routed live-scan full-checkpoint time.
\end{enumerate}

\paragraph{Suggested table note.}

\begin{quote}
The latency column reports isolated kernel timing, while the speedup column is derived from the Python-dispatch chunk-sweep harness. These measurements answer different questions: isolated kernel timing measures device-side scan cost, whereas the harness speedup includes launch and orchestration overhead.
\end{quote}

\subsection*{Can-Keep Items}

The following parts are strong and should be preserved:

\begin{enumerate}
    \item The paper honestly frames COREY as a concept-and-feasibility or diagnostic scheduler rather than a deployment-grade speedup.
    \item The routed path quality-preservation result is valuable: exact greedy-token agreement and zero metric deltas make the latency conclusion cleaner.
    \item The unified routed ablation is stronger than only comparing against passive baseline, because it shows adaptive variants against the best static chunk.
    \item The mixed-regime analysis is useful because it shows that the global static rule is already very close to the per-regime oracle.
    \item The scope limitation to Mamba-1.x is appropriate and should remain explicit.
\end{enumerate}

\subsection*{Shortest Pre-Submission Fix List}

Before submission, complete the following checklist:

\begin{enumerate}
    \item Synchronize all uses of \(H_{\mathrm{ref}}=\log K\) and legacy \(H_{\mathrm{ref}}=8.0\). COREY default must not select both \texttt{chunk=512} and \texttt{chunk=256} for the same setting.
    \item Fix the supplementary PDF layout problems, especially the overlapping table on appendix page 3 and the cropped wide table on appendix page 18.
    \item Make theorem numbering consistent between the main paper and supplementary material.
    \item Submit an anonymous code/data supplement rather than relying only on post-acceptance release.
    \item Add statistical clarification, confidence intervals, or nonparametric tests for small latency deltas.
    \item Replace all occurrences of \texttt{dinner} with \(d_{\mathrm{inner}}\).
    \item Remove review-response wording from the appendix.
    \item Clearly mark Hadamard analysis as prospective and empirically falsified on real Mamba activations.
    \item Ensure every table states whether it reports kernel timing, harness timing, or full-checkpoint generation timing.
    \item Keep the final claim conservative: COREY is output-preserving and diagnostic, but it does not beat the best static chunk on the evaluated checkpoint workloads.
\end{enumerate}

\subsection*{Recommended Final Abstract-Level Claim}

The abstract and conclusion should use conservative language similar to the following:

\begin{quote}
COREY validates entropy-guided runtime chunk scheduling as a quality-preserving diagnostic mechanism for Mamba-1.x selective-scan kernels. At the kernel level, calibrated chunk selection can reproduce the offline-profile oracle. However, in end-to-end routed checkpoint inference, the best static chunk remains faster than all adaptive variants because online feature extraction and dispatch overhead outweigh the marginal benefit of runtime chunk selection. These results identify the regime boundary where adaptive scheduling becomes unnecessary and provide guidance for future fused or device-side scheduler designs.
\end{quote}
