\section*{Review for IEEE Transactions on Circuits and Systems for Video Technology (TCSVT)}

\subsection*{Summary}

This paper presents COREY, an entropy-guided runtime chunk scheduling framework for selective scan kernels in Mamba-style selective state space models (SSMs). The authors investigate whether fixed-bin activation entropy can serve as a lightweight runtime signal for adaptive chunk-size scheduling during inference. The work includes kernel-level benchmarking, runtime overhead analysis, mixed-regime workload evaluation, and routed end-to-end inference experiments.

The paper is technically well organized and contains unusually thorough negative-result reporting. In particular, the authors explicitly acknowledge that entropy-guided adaptive scheduling does not outperform the best static chunk oracle in routed end-to-end inference. The study carefully separates kernel-level oracle gains from deployment-level runtime overheads, which improves scientific transparency and reproducibility.

However, several important concerns remain regarding the practical novelty, deployment significance, theoretical depth, and fit to TCSVT. While the paper demonstrates that entropy-guided scheduling is feasible and output-preserving, the final experimental conclusion is fundamentally negative: the adaptive scheduler is consistently inferior to a simple static scheduling policy or even a trivial sequence-length heuristic. This substantially weakens the practical impact of the contribution.

\subsection*{Overall Recommendation}

\textbf{Recommendation: Weak Reject / Borderline}

The paper is technically sound and reproducible, but its current form does not yet demonstrate sufficient practical performance benefit, systems novelty, or direct video-technology relevance expected by TCSVT.

\subsection*{Strengths}

\begin{itemize}

\item The paper is exceptionally transparent about negative experimental findings, which is uncommon and scientifically valuable.

\item The authors carefully separate:
\begin{itemize}
    \item kernel-level oracle timing,
    \item runtime scheduling overhead,
    \item routed inference cost,
    \item quality preservation.
\end{itemize}

\item The empirical evaluation is extensive and methodologically rigorous:
\begin{itemize}
    \item kernel-level sweeps,
    \item cross-layer entropy analysis,
    \item mixed-regime workload evaluation,
    \item LongBench quality preservation,
    \item cross-hardware comparisons.
\end{itemize}

\item The routed inference experiments preserve exact greedy outputs across all evaluated prompts, demonstrating recurrence-preserving implementation correctness.

\item The reproducibility section is unusually detailed and includes implementation boundaries, hardware distinctions, scheduler assumptions, and measurement-layer separation.

\item The paper includes useful deployment-oriented analysis discussing why adaptive scheduling fails under low entropy variance regimes.

\end{itemize}

\subsection*{Major Concerns}

\subsubsection*{1. The Main Experimental Conclusion is Performance-Negative}

The most significant issue is that the paper's primary deployment-level result is negative.

The routed end-to-end experiments in Table VI explicitly show that:
\begin{itemize}
    \item the best static chunk policy consistently outperforms all entropy-guided variants,
    \item even guarded and learned policies remain slower than the static oracle,
    \item the overhead of entropy computation dominates any scheduling benefit.
\end{itemize}

The paper honestly reports this limitation, but this substantially weakens the practical contribution. The work therefore becomes:
\begin{quote}
``an analysis of why entropy-guided scheduling does not help current Mamba workloads''
\end{quote}
rather than a demonstrated systems acceleration framework.

For TCSVT, where practical deployment benefit is important, the paper currently lacks a convincing positive systems outcome.

\textbf{Suggestion:}
The authors should substantially strengthen one of the following:
\begin{itemize}
    \item a real deployment scenario where entropy scheduling wins,
    \item broader workload heterogeneity,
    \item online serving instability scenarios,
    \item dynamic batch composition,
    \item multimodal/video streaming workloads,
    \item adaptive video-token inference pipelines.
\end{itemize}

Without such evidence, the practical significance remains limited.

\subsubsection*{2. Limited Relevance to TCSVT Scope}

The work focuses almost entirely on:
\begin{itemize}
    \item kernel scheduling,
    \item Triton scan execution,
    \item runtime chunk tuning,
    \item Mamba systems optimization.
\end{itemize}

However, TCSVT primarily emphasizes:
\begin{itemize}
    \item video understanding,
    \item video coding,
    \item visual representation learning,
    \item vision systems,
    \item multimedia intelligence.
\end{itemize}

The current manuscript does not convincingly connect COREY to:
\begin{itemize}
    \item video tasks,
    \item video transformers,
    \item streaming video inference,
    \item visual sequence modeling,
    \item edge-video deployment,
    \item long-video understanding.
\end{itemize}

This creates a scope mismatch risk.

\textbf{Suggestion:}
The paper would significantly benefit from:
\begin{itemize}
    \item experiments on video-oriented Mamba architectures,
    \item evaluation on visual sequence tasks,
    \item latency analysis for video streaming inference,
    \item long-video token scheduling,
    \item video-language model acceleration,
    \item edge video analytics deployment.
\end{itemize}

\subsubsection*{3. Novelty Relative to Existing Runtime Scheduling Literature is Limited}

The paper positions entropy as a runtime scheduling signal, but the actual scheduling formulation is relatively simple:
\[
r = \frac{H}{\log K}
\]
followed by thresholded chunk mapping.

The scheduler itself is heuristic and does not involve:
\begin{itemize}
    \item learned policies,
    \item reinforcement learning,
    \item adaptive optimization,
    \item compiler-assisted scheduling,
    \item online autotuning,
    \item predictive latency modeling.
\end{itemize}

The paper also ultimately concludes that:
\begin{quote}
simple sequence-length heuristics perform equally well or better.
\end{quote}

This weakens the conceptual novelty of the entropy-guided mechanism.

\textbf{Suggestion:}
The authors should better justify:
\begin{itemize}
    \item why entropy is fundamentally superior to sequence length,
    \item when entropy contains unique information,
    \item why entropy-based scheduling should exist at all if sequence length already captures the same routing behavior.
\end{itemize}

\subsubsection*{4. Theoretical Analysis is Weakly Connected to Final Contribution}

The Hadamard entropy majorization analysis occupies substantial space, yet the paper itself repeatedly states:
\begin{itemize}
    \item the theorem assumptions fail on real activations,
    \item the hypothesis is empirically falsified,
    \item the theory is not part of the validated contribution.
\end{itemize}

As a result, a large portion of the theoretical appendix appears disconnected from the actual contribution.

\textbf{Suggestion:}
The paper should either:
\begin{itemize}
    \item greatly reduce the Hadamard discussion,
    \item move it entirely to supplementary material,
    \item or provide a stronger justification for its inclusion.
\end{itemize}

Currently it creates conceptual distraction.

\subsubsection*{5. Lack of Comparison Against Stronger Adaptive Baselines}

The adaptive baselines remain relatively lightweight:
\begin{itemize}
    \item histogram entropy,
    \item moment proxies,
    \item variance,
    \item learned lookup tables.
\end{itemize}

Missing comparisons include:
\begin{itemize}
    \item RL-based runtime schedulers,
    \item hardware-aware autotuners,
    \item TVM/XLA-style online cost models,
    \item compiler-guided adaptive fusion,
    \item CUDA graph specialization,
    \item learned latency prediction networks.
\end{itemize}

Without stronger adaptive baselines, it is difficult to assess whether the negative result is specific to entropy or reflects a broader limitation of adaptive scan scheduling.

\subsection*{Minor Concerns}

\begin{itemize}

\item Some tables are overly dense and difficult to read (especially Tables VI–XVIII).

\item The distinction between:
\begin{itemize}
    \item isolated kernel timing,
    \item routed inference timing,
    \item surrogate timing,
    \item Python dispatch timing
\end{itemize}
is scientifically correct but makes the paper difficult to follow.

\item Several sections repeat similar conclusions regarding:
\begin{quote}
``entropy overhead dominates adaptive benefit''
\end{quote}
which could be consolidated.

\item The manuscript is unusually appendix-heavy relative to the core contribution.

\item Some terminology such as:
\begin{quote}
``validated diagnostic scaffold''
\end{quote}
is somewhat vague and should be made more concrete.

\item The paper would benefit from clearer visual figures illustrating:
\begin{itemize}
    \item routing behavior,
    \item entropy distributions,
    \item scheduling overhead decomposition,
    \item chunk selection transitions.
\end{itemize}

\end{itemize}

\subsection*{Questions for the Authors}

\begin{enumerate}

\item Can the authors demonstrate a workload where entropy-guided scheduling actually outperforms the best static chunk policy?

\item Why is entropy preferable to sequence length if the mixed-regime study shows sequence length alone matches the oracle?

\item How sensitive are the conclusions to:
\begin{itemize}
    \item larger Mamba checkpoints,
    \item Mamba-2,
    \item RWKV-style recurrence,
    \item video-oriented SSM architectures?
\end{itemize}

\item Can the routing mechanism operate entirely inside a fused CUDA/Triton kernel without Python dispatch overhead?

\item Is there any realistic deployment scenario where the entropy estimation cost becomes amortized?

\end{enumerate}

\subsection*{Reproducibility}

The reproducibility quality is strong.

The paper provides:
\begin{itemize}
    \item implementation details,
    \item scheduler hyperparameters,
    \item hardware descriptions,
    \item timing-layer separation,
    \item runtime hook definitions,
    \item workload construction methodology.
\end{itemize}

The CodeOcean repository link is appreciated and improves transparency.

\subsection*{Final Assessment}

This paper is scientifically honest and technically careful. The authors deserve credit for transparently reporting negative deployment results rather than overstating practical gains.

However, for TCSVT publication standards, the current manuscript still suffers from several issues:
\begin{itemize}
    \item limited video-technology relevance,
    \item lack of positive deployment advantage,
    \item relatively modest scheduling novelty,
    \item heavy reliance on negative findings,
    \item insufficient comparison against stronger adaptive systems baselines.
\end{itemize}

The work may become substantially stronger if extended toward:
\begin{itemize}
    \item long-video inference,
    \item streaming visual transformers,
    \item multimodal sequence systems,
    \item fused-kernel deployment,
    \item adaptive edge-video acceleration.
\end{itemize}

At its current stage, I lean toward \textbf{Weak Reject / Borderline Reject}.
